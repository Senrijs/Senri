# 0.3.0 の設計メモ

> 状態: 1 は案 B に決定(P1 で、書き方を `endpoint()` と 2 段の前置きに直した)。2〜4 は案。

0.3.0 の目標は「本番まで届く」(ROADMAP)。このメモでは、そのうち API の形に関わるものを先に決める。

- 1. 型付きクライアント(RPC)の形
- 2. OpenAPI の生成
- 3. テスト用ヘルパー
- 4. 壊れる変更の一覧(0.3.0 にまとめて入れるもの)と、移行のしかた

前提:

- 本体(`@senrijs/senri`)は大きくしない。クライアントは別の入口(`@senrijs/senri/client`)にする
- どのランタイム(Bun・Deno・Node.js・Workers・ブラウザ)でも同じに動く
- スキーマは Standard Schema のまま(特定のライブラリに依存しない)
- 後で Ippo(Senri の上に乗る React のメタフレームワーク)の loader やサーバー関数の型にも使える形にする

---

## 1. 型付きクライアント(RPC)の形

### 1.1 何が問題か

今の書き方では、ルートを 1 つずつ別の文で登録する。

```ts
const app = createApp();
app.get("/users/:id", ({ id }) => ({ id, name: "a" }));
app.post("/users", { body: userSchema }, (_, c) => ({ created: c.valid("body") }));
```

`app.get()` は `void` を返す。TypeScript では、文を重ねても変数 `app` の型は変わらないので、「このアプリには、どのルートがあるか」が型に積み上がらない。クライアントに渡せる型がない。

クライアントに届けたいもの:

| もの | 今どこにあるか |
|---|---|
| メソッドとパス | `app.get("/users/:id", ...)` の文字列 |
| パスパラメーター | パスから型を取り出している(`ExtractParams`)。`params` のスキーマがあれば、その型 |
| クエリ | `query` のスキーマ(`RouteSchemas`) |
| ボディ | `body` のスキーマ |
| レスポンス | ハンドラーの戻り値の型(文字列 → テキスト、オブジェクト → JSON) |

注意: クライアントが送る型は、スキーマの**入力**の型(`InferInput`)。今の Senri は、ハンドラーが受け取る**出力**の型(`InferOutput`)しか扱っていない。

### 1.2 ほかのフレームワークのやり方

| | 型の積み上げ方 | クライアントの呼び方 | 良いところ | 困るところ |
|---|---|---|---|---|
| Hono の `hc` | メソッドをつなげて書く(`app.get().post()`)。`typeof` したものを渡す | `client.users[":id"].$get({ param: { id } })`(Proxy) | 今の Hono の書き方に、つなげるだけで付く。レスポンスの型を status ごとに分けられる(`c.json(x, 404)`) | つなげ忘れると型が消える(エラーにならない)。ルートが増えると tsserver が重い(公式に「分けて、tsc で先に型を作る」と案内)。`onError`・ミドルウェア・`notFound` の応答は型に入らない。フロントとバックで Hono の版がずれると「型が深すぎる」エラー |
| Elysia の Eden Treaty | メソッドをつなげて書く。`typeof app` を渡す | `api.users({ id }).get()`(Proxy。パスの `/` が `.`) | 呼び方が自然。`{ data, error }` で返る | Hono と同じく、つなげる書き方が前提。型の重さも同じ問題を持つ。Elysia の作りに強く結び付いている |
| tRPC | 手続き(procedure)をオブジェクトにまとめる(router) | `trpc.user.byId.query({ id })` | 1 つのオブジェクトなので、型が一度で決まる。軽い | HTTP の形(メソッド・パス・status)を持たない。REST や OpenAPI は外部のもの頼み。今の Senri の書き方とまったく違う |
| oRPC | 手続きをオブジェクトにまとめる。HTTP のメソッドとパスは、手続きごとに付けられる | `client.planet.list({ ... })` | Standard Schema をそのまま使う。同じ定義から OpenAPI を出せる。コード生成がない | tRPC と同じく、手続きが中心(パスは後から付けるもの)。今の Senri の書き方とは違う |

まとめると、

- **つなげて書く形**(Hono・Elysia)は、今のフレームワークの書き方を残せるが、型が重く、つなげ忘れに気づけない
- **オブジェクトにまとめる形**(tRPC・oRPC)は、型が一度で決まって軽いが、HTTP の形から離れる
- **型を生成する形**は、どこも主な道にはしていない(OpenAPI からクライアントを作る道具はある)

### 1.3 案

#### 案 A: メソッドをつなげて書く形(Hono・Elysia と同じ)

`app.get()` などが、ルートを足した型のアプリを返すようにする。

```ts
const app = createApp()
    .get("/users/:id", ({ id }) => ({ id, name: "a" }))
    .post("/users", { body: userSchema }, (_, c) => ({ created: c.valid("body") }));

export type Api = typeof app;

// クライアント
const api = client<Api>("https://example.com");
const res = await api.users[":id"].$get({ params: { id: "1" } });
```

- **今の書き方:** 壊さない(`void` を返していたものが、アプリを返すようになるだけ)。ただし、型が欲しければ全部をつなげて書き直す必要がある。別々の文で書いたルートは、黙って型から消える
- **`createRouter` と `app.route()`:** これらもつなげて書く形にする必要がある
- **型:** パラメーター・クエリ・ボディ・レスポンスは届けられる。ルートが増えるほど型の計算が重くなる(ルートごとに、アプリ全体の型を作り直すため)
- **本体のサイズ:** 戻り値を `this` にするだけなので、ほぼ増えない(数十バイト)
- **Ippo:** ルートが「アプリの型の一部」としてしか存在しないので、loader やサーバー関数 1 つ分の型を取り出すのに、型の掘り出しが要る

#### 案 B: ルートをまとめて定義する形(今の `app.routes()` を伸ばす)

Senri には、表の形でまとめて登録する `app.routes({ "GET /hello": handler })` が既にある。この表を、型を持ったまま外に出せるようにする。

```ts
import { createApp, defineRoutes, endpoint } from "@senrijs/senri";

export const routes = defineRoutes({
    "GET /users/:id": ({ id }) => ({ id, name: "a" }),
    "POST /users": endpoint({ body: userSchema }, (_, c) => ({ created: c.valid("body") })),
});
export type Api = typeof routes;

const app = createApp();
app.routes(routes);

// クライアント(@senrijs/senri/client)
const api = client<Api>("https://example.com");
const user = await api("GET /users/:id", { params: { id: "1" } });
```

- **今の書き方:** 壊さない。`app.get()` はそのまま使える(ただし、そのルートはクライアントの型に入らない)。型が欲しいルートだけ表に移せばよい
- **今の表との違い:** 今の `app.routes()` の表は、値がハンドラーだけで、スキーマを付けられない(`RouteTable` の型も、ハンドラーの戻り値の型を捨てている)。案 B では、スキーマ付きのルート(`endpoint(schemas, handler)`)も置けるようにし、戻り値の型を保つ
- **まとめ方:** 表は普通のオブジェクトなので、ファイルごとに分けて合わせられる(`mergeRoutes()`)。前置きは表を作るときに付ける(1.7)
- **型:** キー(`"GET /users/:id"`)からメソッドとパスとパラメーターが決まる。表は 1 つのオブジェクトリテラルなので、型は一度で決まり、ルートが増えても作り直しがない。ハンドラーの戻り値の型を保つよう、`RouteTable` の型を作り直す(型だけの変更)
- **クライアントの呼び方:** サーバーの表と同じ `"GET /users/:id"` という文字列で呼ぶ。Proxy を使わないので、クライアントの実行時のコードが小さい(パスにパラメーターを入れ、クエリとボディを付けて `fetch` するだけ)。文字列なので、検索でサーバーのルートとすぐ結び付く
- **本体のサイズ:** `defineRoutes` は、受け取った表をそのまま返す関数(型を付けるためだけ)。本体はほぼ増えない。クライアントは別の入口
- **Ippo:** 表の 1 つ 1 つが独立した定義なので、`typeof routes["GET /users/:id"]` で 1 つのルートの入力と出力の型を取り出せる。loader(GET)やサーバー関数(POST)の型にそのまま使える
- **OpenAPI(2 で詳しく):** 表は実行時にも一覧できて、スキーマも横にあるので、そのまま元にできる

#### 案 C: 型を生成する形

今の書き方はそのままにして、ビルドの前にアプリを読み、ルートの型をファイルに書き出す。

```sh
senri gen client ./src/app.ts > ./client/api.d.ts
```

- **今の書き方:** まったく変えなくてよい
- **型:** メソッド・パス・パラメーター・スキーマは、実行時にアプリから取れる(`app.routeList()` とスキーマ)。しかし**レスポンスの型(ハンドラーの戻り値)は実行時には分からない**ので、TypeScript のコンパイラー API で読む必要がある。重く、壊れやすい
- **開発の流れ:** サーバーを変えるたびに生成し直す。忘れると、型が古いまま通ってしまう(CI で確かめる仕組みが要る)
- **本体のサイズ:** 増えない(生成の道具は別のパッケージ)
- **Ippo:** 生成したファイルを読めば使えるが、メタフレームワークの中で生成の手順を持つことになる

### 1.4 比べ

| | 案 A: つなげて書く | 案 B: まとめて定義 | 案 C: 型を生成 |
|---|---|---|---|
| 今の書き方を壊さないか | 壊さない(型が欲しければ全部書き直し) | 壊さない(欲しいルートだけ表へ) | 壊さない |
| 書き忘れたとき | 黙って型から消える | 表にないルートは、クライアントに出ない(はっきりしている) | 生成し忘れると古い型のまま |
| パラメーター・クエリ・ボディ | 届く | 届く | 届く |
| レスポンスの型 | 届く | 届く | コンパイラー API が要る |
| 型の重さ(ルートが多いとき) | 重い(Hono が公式に注意) | 軽い(一度で決まる) | 軽い(生成済み) |
| 本体のサイズ | ほぼ増えない | ほぼ増えない | 増えない |
| クライアントの実行時のコード | Proxy | 関数 1 つ | 関数 1 つ(生成物) |
| OpenAPI の元にできるか | アプリの中を一覧すれば | 表をそのまま使える | 生成の道具の中で |
| Ippo の loader・サーバー関数 | 型の掘り出しが要る | 1 つずつ取り出せる | 生成物から |

### 1.5 決めたこと: 案 B(ルートをまとめて定義する形)

案 B で進める。理由:

1. **今の Senri の上に自然に乗る。** 表の形の `app.routes()` は既にある。新しい書き方を足すのではなく、今あるものに型を持たせる
2. **壊す変更がない。** `app.get()` の書き方はそのまま残る。型付きクライアントが欲しいルートだけ、表に移せばよい
3. **型が軽い。** Hono が公式に注意している「ルートが増えると tsserver が重い」問題を、作りの段階で避けられる
4. **書き忘れに気づける。** 「つなげ忘れて型が黙って消える」ことがない。表にあるものが、クライアントに出るもの
5. **2〜3 と Ippo にそのまま使える。** 表は実行時にも一覧できて、スキーマも横にあるので、OpenAPI とテスト用ヘルパーの元になる。1 つのルートの型を取り出せるので、Ippo の loader やサーバー関数にも使える

型の扱いで決めたこと:

| こと | 決めたこと |
|---|---|
| レスポンスの型 | まず**成功の型だけ**(ハンドラーの戻り値から `Response` を除いたもの)。status ごとの型は、書きたい人だけ書ける(1.8) |
| `onError`・ミドルウェアの応答 | **型に入れない**。クライアントは、成功でない応答を `error`(中身は `unknown`)として返す |
| `Date` など | クライアントの型は、**JSON にしたあとの形**にする(`Date` → `string`、`undefined` のプロパティは消える、`toJSON()` があればその戻り値) |
| 文字列を返すハンドラー | クライアントの型は `string`(テキストとして読む) |

### 1.6 表の書き方

値は、ハンドラーだけか、スキーマを付けたルート(`endpoint()` で包む)。

```ts
import { defineRoutes, endpoint } from "@senrijs/senri";

export const userRoutes = defineRoutes("/users")({
    // ハンドラーだけ(パラメーターはキーから)
    "GET /:id": ({ id }) => ({ id, name: "a" }),
    // スキーマを付ける。endpoint(schemas, handler) は、今の app.post(path, schemas, handler) の 2 つ目と 3 つ目の引数
    "POST /": endpoint({ body: userSchema }, (_, c) => ({ created: c.valid("body") })),
});
```

- 前置きは 2 段で書く: `defineRoutes(prefix)(table)`。前置きがなければ 1 段: `defineRoutes(table)`
- 戻り値は、キーに前置きを付けた表(`"GET /users/:id"`、`"POST /users"`)。型も同じく付け直す
- `"POST /"` に前置きを付けると `"POST /users"`(末尾の `/` は付けない。今のルーターと同じく、末尾のスラッシュは区別しない)
- 前置きは `/` で始め、`/` で終わらない。`""` と `"/"` は前置きなしと同じ
- キーの書き間違い(メソッドとパスの間に空白がない、など)は、今の `RouteTable` と同じく型のエラーにする
- 実行時のチェック(パスの `*` の位置、パラメーター名、同じルートの 2 回登録など)は、`app.routes()` に渡したときに、今の `app.get()` と同じ処理で行う
- `c.get()` に型を付けるときは、前置きと一緒にアプリの型を渡す: `defineRoutes<"/admin", Vars>("/admin")({ ... })`(`createRouter<"/admin", Vars>("/admin")` と同じ)

**この書き方にした理由(P1 で試して分かったこと。TypeScript 7.0.2):**

- **スキーマ付きを `{ body, handler }` のオブジェクトにすると、型が付かない。** スキーマの型はルートごとに違うので、1 回の呼び出しの中では推論できない(表全体が `unknown` になるか、`c.valid("body")` の型が消える)。`endpoint()` で包めば、スキーマの型はその呼び出しの中で決まり、パスのパラメーターの型は、置かれた場所(表のキー)から推論される
- **前置きと表を同じ呼び出しに渡すと、ハンドラーの引数に型が付かない。** 前置きの型を推論しながら、同じ呼び出しの中で引数の型を決めることができない(`defineRoutes(prefix, table)` も、`defineRoutes({ prefix, routes })` も同じ)。前置きを先に決める 2 段にすれば付く
- 名前は `route()` ではなく `endpoint()`。`app.route(prefix, subApp)` と紛らわしくしないため

### 1.7 ファイルを分けるとき(合わせ方と前置き)

**前置きは、表を作るときに付ける。** あとから付ける形(`prefix("/orgs/:orgId", table)`)にすると、中のハンドラーが `orgId` の型を知らない。これは今の `createRouter(prefix)` が、前置きを作るときに決めている理由と同じ。

```ts
// routes/orgs.ts — 前置きのパラメーターも、中のハンドラーで型が付く
export const orgRoutes = defineRoutes("/orgs/:orgId")({
    "GET /members": ({ orgId }) => listMembers(orgId),
    "GET /members/:memberId": ({ orgId, memberId }) => getMember(orgId, memberId),
});

// routes/index.ts — 表を合わせる
import { mergeRoutes } from "@senrijs/senri";
export const routes = mergeRoutes(userRoutes, orgRoutes, defineRoutes({ "GET /health": () => "ok" }));
export type Api = typeof routes;

// app.ts
app.routes(routes);
```

- **`mergeRoutes(...tables)`:** 表を 1 つにする。型は、それぞれの表の型を合わせたもの。**同じキーが 2 つあったら、実行時にエラーにする**(スプレッド `{ ...a, ...b }` だと、黙って後ろが勝つので勧めない)
- **入れ子:** `api` の下にさらに分けたいときは、`defineRoutes("/api/users")(...)` のように、表を作るときに全部の前置きを書く。前置きをあとから重ねる関数は作らない(パラメーターの型が崩れるため)。前置きを定数にしておけば、書き間違いは防げる
  ```ts
  const API = "/api";
  export const userRoutes = defineRoutes(`${API}/users`)({ ... }); // 型は "/api/users" のまま残る
  ```
- **型の確かめ方:** 型のテストに、前置きのパラメーター・合わせたあとのキーを入れる(P1 で入れた)。重ねたときの型の重さ(200 ルート)は P3 で測る

### 1.8 ルートごとのミドルウェア

今は `app.use(path, mw)` でパスごとにしか付けられない。表では、ルートごと(と、表ごと)に付けられるようにする。

```ts
// この表の全部のルートに付ける: 前置きのあとに { use }(前置きがなければ "")
export const adminRoutes = defineRoutes("/admin", { use: [auth()] })({
    "GET /stats": (_, c) => stats(c.get("user")),
    // このルートだけに付ける: endpoint() の 1 つ目の引数に use
    "DELETE /users/:id": endpoint({ use: [requireRole("owner")], params: idSchema }, ({ id }) => deleteUser(id)),
});
```

- **順番:** アプリの `app.use()` → 表の `use` → ルートの `use` → スキーマの確認 → ハンドラー。認証が先に動き、通らなければスキーマの確認(本文を読む)の前に止まる
- **`c.get()` の型:** `auth()` が `c.set("user", user)` するなら、ミドルウェアの型(`Middleware<{ user: User }>`)から、ハンドラーの `c.get("user")` に型が付くようにする(表とルートの `use` の型を合わせる)
- **応答の型:** ミドルウェアが返す応答(401 など)は、型に入れない(1.5)
- **今の `app.use(path, mw)` との関係:** そのまま残す。パスで付けるものと、ルートに付けるものの 2 つになる。開発モードのダッシュボードの「ルートとミドルウェア」に、ルートごとのものも出す
- **本体のサイズ:** ルートのハンドラーを、ミドルウェアごと包む処理を足す(今の `compose` を使う)。数百バイト(gzip で 100〜200 バイト)の見込み

### 1.9 status ごとの型(書きたい人だけ)

`c.json(body, status)` と `c.text(body, status)` の戻り値の型に、status と本文の型を残す(実行時は今と同じ `Response`。型だけの変更)。

```ts
"GET /users/:id": ({ id }, c) => {
    const user = find(id);
    if (!user) return c.json({ message: "not found" }, 404);
    return user;
},
```

クライアントでは、こう分かれる。

```ts
const res = await api("GET /users/:id", { params: { id: "1" } });
if (res.ok) res.data;        // User(JSON にしたあとの形)
else if (res.status === 404) res.error; // { message: string }
else res.error;               // unknown(onError やミドルウェアの応答)
```

- 何も書かなければ、成功の型だけ(`res.data`)。`res.error` は `unknown`
- `c.json(..., 200)` のように 2xx を書いたものは、成功の型に足す

### 1.10 クライアント(`@senrijs/senri/client`)

```ts
import { client } from "@senrijs/senri/client";
import type { Api } from "../server/routes";

const api = client<Api>("https://example.com", { headers: { authorization: "Bearer ..." } });
const res = await api("GET /users/:id", { params: { id: "1" }, query: { full: "1" } });
```

- 呼び方は、表のキーと同じ文字列。パラメーターをパスに入れ(エンコードする)、クエリを付け、ボディを JSON(または `FormData` / `URLSearchParams` ならそのまま)で送る
- 戻り値は `{ ok, status, data, error, response }`。成功でなくても例外にしない(ネットワークのエラーだけは例外)
- 本文は Content-Type で読み分ける(JSON / テキスト / それ以外は `Blob`)
- `fetch` を差し替えられる(3 のテスト用ヘルパーと、Workers の Service Binding で使う)
- 送る型はスキーマの**入力**の型(`InferInput` を足す)。パラメーターとクエリは、スキーマがなければ文字列
- Proxy を使わないので小さい。目標は minify 後 1KB 前後(本体には入らない)

### 1.11 本体のサイズ

**目標: `bun run size` の最小アプリ(hi)で、gzip 後 7KB 以下**(0.2.21 で 6.3KB)。

| 足すもの | 本体に入るか | 見込み |
|---|---|---|
| `defineRoutes` / `mergeRoutes` | 入る(表を使わないアプリでも、`index.ts` から出るので) | 両方で gzip 100 バイト前後 |
| `endpoint()`・ルートごとのミドルウェア | 入る | gzip 100〜200 バイト |
| 型(`InferInput`、status の型、JSON にした形) | 入らない(型だけ) | 0 |
| クライアント | 入らない(`/client`) | — |
| OpenAPI | 入らない(`/openapi`) | — |
| テスト用ヘルパー | 入らない(`/testing`) | — |

合わせて gzip 300 バイト前後の見込みで、7KB に収まる。作る PR ごとに `bun run size` で確かめる。

## 2. OpenAPI の生成

### 2.1 何から作るか

**1 の表(`defineRoutes` の戻り値)から作る。** 表は実行時にも一覧できて、メソッド・パス・スキーマが横にあるので、そのまま元になる。

```ts
import { openAPI } from "@senrijs/senri/openapi";

const doc = openAPI(routes, {
    info: { title: "My API", version: "1.0.0" },
});
app.get("/openapi.json", () => doc);
```

- 表にない `app.get()` のルートは、入れない(スキーマもレスポンスの形も分からないため)。入れたいなら、表に移す
- 出すのは **OpenAPI 3.1**(JSON Schema 2020-12 をそのまま使える版)。3.0 が要る人のために `version: "3.0"` を選べるようにする(2.2 の `openapi-3.0` の形に変える)
- 別の入口(`@senrijs/senri/openapi`)。本体は増えない

### 2.2 Standard Schema から JSON Schema へ

Standard Schema とは別に、**Standard JSON Schema**(https://standardschema.dev/json-schema)という仕様がある。スキーマが `~standard.jsonSchema.input({ target })` / `.output({ target })` を持ち、JSON Schema を返す。`target` は `"draft-2020-12"`・`"draft-07"`・`"openapi-3.0"`。

| ライブラリ | Standard JSON Schema の対応 |
|---|---|
| Zod | 4.2 から。スキーマにそのまま付いている |
| Zod Mini | 4.2 から。`z.toJSONSchema()` 経由 |
| ArkType | 2.1.28 から |
| Valibot | 1.2 から。`@valibot/to-json-schema`(1.5 から)の `toStandardJsonSchema()` で包む |
| VineJS | 4.3.0 から |
| Sury | 11.0.0-alpha.10 から(`S.enableStandardJSONSchema()`) |
| stnl | 2.1 から |

方針:

1. スキーマに `~standard.jsonSchema` があれば、それを使う。リクエスト(params・query・body)は **`input`**、レスポンスは **`output`**(変換で形が変わるライブラリでも、送る側と受ける側の形が正しくなる)
2. なければ、利用者が渡す変換の関数を使う(`openAPI(routes, { toJSONSchema: (schema) => ... })`。古い版のライブラリ向け)
3. どちらもなければ、そのスキーマは空(`{}`)にして、「このルートのスキーマは JSON Schema にできない」と知らせる。黙って抜かさない(P5 では、開発モードに限らず `openAPI()` を呼んだときに `onWarning`(既定は `console.warn`)で知らせることにした。`openAPI()` は開発モードの外でも呼ぶため)
4. 変換が例外を投げたら(JSON Schema で表せない形)、3 と同じく知らせる

ほかのフレームワーク:

- Hono: `@hono/zod-openapi`(Zod 専用。ルートを別の形で定義し直す)と、`hono-openapi`(Standard Schema 向け。ライブラリごとの変換を使う)
- Elysia: `@elysiajs/openapi`。TypeBox(Elysia の `t`)はそのまま JSON Schema。ほかのライブラリは変換を渡す
- oRPC: 標準で OpenAPI を出せる。ライブラリごとの変換(`@orpc/zod` など)を渡す
- Senri は、Standard JSON Schema を優先するので、**ライブラリごとの変換のパッケージを持たずに済む**

### 2.3 ルートから OpenAPI の各部分へ

| 表にあるもの | OpenAPI |
|---|---|
| キーのメソッドとパス(`"GET /users/:id"`) | `paths["/users/{id}"].get`(`:id` → `{id}`。ワイルドカード `*` は `{*}` にできないので、`{path}` という名前のパラメーターにして説明を付ける) |
| パスパラメーター | `parameters`(`in: path`)。`params` のスキーマがあれば、各プロパティの型。なければ文字列 |
| `query` のスキーマ | `parameters`(`in: query`)。スキーマはオブジェクトである必要がある(違えば開発モードで知らせる) |
| `body` のスキーマ | `requestBody`(`application/json`)。フォームで受けるルートは、`endpoint({ body, bodyType: "form" }, ...)` のように書けるようにする(既定は JSON) |
| レスポンス | ハンドラーの戻り値の型は実行時に分からない。**`endpoint({ response }, ...)` でスキーマを書いたものだけ**、`responses["200"]` に出す。書かなければ説明だけの 200 |
| status ごとのレスポンス | `responses: { 404: schema }` のように書いたものだけ |
| ルートの `use`(認証など) | 自動では出さない。`openAPI(routes, { security })` や、`endpoint({ openapi: { security: [...] } }, ...)` で書く |
| 説明 | `endpoint({ openapi: { summary, description, tags, operationId } }, ...)` で書ける(OpenAPI の項目そのまま) |

- `response` のスキーマは、OpenAPI のためだけに書くもの。開発モードでは、ハンドラーの戻り値をそのスキーマで確かめて、ずれていたら知らせる(本番では確かめない。速さのため)
- `response` のスキーマを書いたら、クライアントの型もそのスキーマの出力の型にする(ハンドラーの戻り値より優先)。P5 ではまだ入れていない(P3 のクライアントと別のブランチで作ったため)。P3・P5 が main に入ったあとで足す

## 3. テスト用ヘルパー

### 3.1 RPC のクライアントをそのまま使う

クライアントは `fetch` を差し替えられる(1.10)ので、`app.fetch` を渡せば、サーバーを立てずに同じクライアントでテストできる。これを入口にまとめる。

```ts
import { testClient } from "@senrijs/senri/testing";
import type { Api } from "./routes";

const api = testClient<Api>(app);
const res = await api("POST /users", { body: { name: "a" } });
expect(res.status).toBe(201);
```

`testClient` がすること:

- ベース URL を `http://localhost` にして、`app.fetch` を直接呼ぶ
- 接続元を `127.0.0.1` として渡す(`getIp()`・`ipRestriction()`・開発モードの localhost 判定が、本物のサーバーと同じに動く)
- Workers のアプリ向けに、`env` と `ctx` を渡せる(`testClient(app, { env, ctx })`。`c.env`・`c.executionCtx` が使える)
- ヘッダーを毎回付けられる(`{ headers }`)。Cookie は、前の応答の `Set-Cookie` を次のリクエストに付ける(`{ cookies: true }` で有効。ログインのテスト向け)

### 3.2 型付きでないリクエスト

表にないルートや、壊れたリクエストを送るテストのために、型のない形も用意する。

```ts
import { request } from "@senrijs/senri/testing";
const res = await request(app, "GET /old-route", { headers: { "x-a": "1" } });
// res は普通の Response
```

- `app` に `app.request()` のようなメソッドは足さない(本体を大きくしないため。Hono には `app.request()` がある)

## 4. 壊れる変更の一覧と、移行のしかた

0.3.0 にまとめて入れる。1〜3 は足すだけなので、ここに入るのは主に 4.1〜4.2。

### 4.1 意図せず公開しているものを隠す

| 今あるもの | 入口 | 移行のしかた |
|---|---|---|
| `parseCookies(header)` | `@senrijs/senri/cookie` | `getCookie(c)`(全部)・`getCookie(c, name)`(1 つ)を使う |
| `serializeCookie(name, value, options)` | `@senrijs/senri/cookie` | `setCookie(c, name, value, options)` を使う |
| `deletionCookie(name, options)` | `@senrijs/senri/cookie` | `deleteCookie(c, name, options)` を使う |
| `resolvePort()`・`DEFAULT_PORT`・`PortSource` | `@senrijs/senri/serve` | `serve()` がポートを決める(`port` → `PORT` → 3927)。決まったポートは `server.port` で読む |
| `isLocalUrl(url)` | `@senrijs/senri/dev` | 代わりは出さない(開発モードの中の判定。使っている人は、自分で `new URL(url).hostname` を見る) |

- 公開の型が、公開していない型を参照しないようにする(JSR のスコアと、`.d.ts` のわかりやすさのため)
- 注意: ドキュメントサイト(`docs/website/scripts/home-data.ts`)が `resolvePort` / `DEFAULT_PORT` を使っている。サイトの中で値を持つように直す

### 4.2 本文の大きさの既定の上限

#89 のときに出した案(0.3.0 で決めることにしたもの)をそのまま入れる。

| 変わること | 今 | 0.3.0 | 移行のしかた |
|---|---|---|---|
| 本文を全部読む関数(`c.body()`、ルートの `body` のスキーマ、`c.req.json()` / `text()` / `formData()` / `arrayBuffer()`)の上限 | なし | **1 MiB**(`createApp({ maxBodySize })` で変える。`Infinity` で外す) | 大きい本文を受けるルートだけ `bodyLimit({ maxSize })` を付ける(ルートの `bodyLimit()` は既定の上限を**置き換える**)。アプリ全体で変えるなら `createApp({ maxBodySize })` |
| `multipart()` の `maxTotalSize` の既定 | `Infinity` | **100 MiB**(`maxFileSize` をそれより大きくして `maxTotalSize` を書かなければ、`maxFileSize` に合わせる) | 100 MiB を超える合計を受けるなら `maxTotalSize` を書く |
| Bun の `serve()` の本文の上限 | 128 MiB(`Bun.serve` の既定) | **上限なし**(Node.js・Deno とそろえる。守りは 1 MiB の既定と、ルートごとの上限) | なし。サーバー全体で上限が要るなら `serve(app, { maxRequestBodySize })` |

- 超えたときは、どれも 413
- 本文を読まないルートには、何も変わらない(上限は読むときにだけかかる)
- Node.js の近道を壊さないよう、数えるのはアダプターの読み込みの中で行う。#88 のベンチで速さを確かめる
- ルートごとのミドルウェア(1.8)と合わせて、表のルートに `use: [bodyLimit({ maxSize })]` で付けられる

### 4.3 1〜3 で壊すことになったもの

| 変わること | 誰に影響するか | 移行のしかた |
|---|---|---|
| `RouteTable` の型が、ハンドラーの戻り値の型を保つ形になる(値に `endpoint()` も入る) | `RouteTable<...>` を自分で型注釈に書いている人だけ(実行時は変わらない) | 型注釈を外すか、`defineRoutes()` を使う |
| `c.json()` / `c.text()` の戻り値の型が、`Response` の部分型(`TypedResponse<...>`)になる | ない見込み(`Response` として扱えるまま)。`ReturnType<typeof c.json>` を `Response` と比べているような型のテストだけ | 型のテストを直す |

実行時の動きが変わる壊れる変更は、1〜3 にはない。
