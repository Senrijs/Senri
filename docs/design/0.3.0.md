# 0.3.0 の設計メモ

> 状態: 下書き。1(型付きクライアント)の比べまで。2〜4 は、1 の方針が決まってから書く。

0.3.0 の目標は「本番まで届く」(ROADMAP)。このメモでは、そのうち API の形に関わるものを先に決める。

- 1. 型付きクライアント(RPC)の形
- 2. OpenAPI の生成
- 3. テスト用ヘルパー
- 4. 壊れる変更の一覧(0.3.0 にまとめて入れるもの)と、移行のしかた

前提:

- 本体(`@senrijs/senri`)は大きくしない。クライアントは別の入口(`@senrijs/senri/client`)にする
- どのランタイム(Bun・Deno・Node.js・Workers・ブラウザ)でも同じに動く
- スキーマは Standard Schema のまま(特定のライブラリに依存しない)
- 後で Ippo(Senri の上に乗る React のメタフレームワーク)の loader やサーバー関数の型にも使える形にする

## 1. 型付きクライアント(RPC)の形

### 1.1 何が問題か

今の書き方では、ルートを 1 つずつ別の文で登録する。

```ts
const app = createApp();
app.get("/users/:id", ({ id }) => ({ id, name: "a" }));
app.post("/users", { body: userSchema }, (_, c) => ({ created: c.valid("body") }));
```

`app.get()` は `void` を返す。TypeScript では、文を重ねても変数 `app` の型は変わらないので、「このアプリには、どのルートがあるか」が型に積み上がらない。クライアントに渡せる型がない。

クライアントに届けたいもの:

| もの | 今どこにあるか |
|---|---|
| メソッドとパス | `app.get("/users/:id", ...)` の文字列 |
| パスパラメーター | パスから型を取り出している(`ExtractParams`)。`params` のスキーマがあれば、その型 |
| クエリ | `query` のスキーマ(`RouteSchemas`) |
| ボディ | `body` のスキーマ |
| レスポンス | ハンドラーの戻り値の型(文字列 → テキスト、オブジェクト → JSON) |

注意: クライアントが送る型は、スキーマの**入力**の型(`InferInput`)。今の Senri は、ハンドラーが受け取る**出力**の型(`InferOutput`)しか扱っていない。

### 1.2 ほかのフレームワークのやり方

| | 型の積み上げ方 | クライアントの呼び方 | 良いところ | 困るところ |
|---|---|---|---|---|
| Hono の `hc` | メソッドをつなげて書く(`app.get().post()`)。`typeof` したものを渡す | `client.users[":id"].$get({ param: { id } })`(Proxy) | 今の Hono の書き方に、つなげるだけで付く。レスポンスの型を status ごとに分けられる(`c.json(x, 404)`) | つなげ忘れると型が消える(エラーにならない)。ルートが増えると tsserver が重い(公式に「分けて、tsc で先に型を作る」と案内)。`onError`・ミドルウェア・`notFound` の応答は型に入らない。フロントとバックで Hono の版がずれると「型が深すぎる」エラー |
| Elysia の Eden Treaty | メソッドをつなげて書く。`typeof app` を渡す | `api.users({ id }).get()`(Proxy。パスの `/` が `.`) | 呼び方が自然。`{ data, error }` で返る | Hono と同じく、つなげる書き方が前提。型の重さも同じ問題を持つ。Elysia の作りに強く結び付いている |
| tRPC | 手続き(procedure)をオブジェクトにまとめる(router) | `trpc.user.byId.query({ id })` | 1 つのオブジェクトなので、型が一度で決まる。軽い | HTTP の形(メソッド・パス・status)を持たない。REST や OpenAPI は外部のもの頼み。今の Senri の書き方とまったく違う |
| oRPC | 手続きをオブジェクトにまとめる。HTTP のメソッドとパスは、手続きごとに付けられる | `client.planet.list({ ... })` | Standard Schema をそのまま使う。同じ定義から OpenAPI を出せる。コード生成がない | tRPC と同じく、手続きが中心(パスは後から付けるもの)。今の Senri の書き方とは違う |

まとめると、

- **つなげて書く形**(Hono・Elysia)は、今のフレームワークの書き方を残せるが、型が重く、つなげ忘れに気づけない
- **オブジェクトにまとめる形**(tRPC・oRPC)は、型が一度で決まって軽いが、HTTP の形から離れる
- **型を生成する形**は、どこも主な道にはしていない(OpenAPI からクライアントを作る道具はある)

### 1.3 案

#### 案 A: メソッドをつなげて書く形(Hono・Elysia と同じ)

`app.get()` などが、ルートを足した型のアプリを返すようにする。

```ts
const app = createApp()
    .get("/users/:id", ({ id }) => ({ id, name: "a" }))
    .post("/users", { body: userSchema }, (_, c) => ({ created: c.valid("body") }));

export type Api = typeof app;

// クライアント
const api = client<Api>("https://example.com");
const res = await api.users[":id"].$get({ params: { id: "1" } });
```

- **今の書き方:** 壊さない(`void` を返していたものが、アプリを返すようになるだけ)。ただし、型が欲しければ全部をつなげて書き直す必要がある。別々の文で書いたルートは、黙って型から消える
- **`createRouter` と `app.route()`:** これらもつなげて書く形にする必要がある
- **型:** パラメーター・クエリ・ボディ・レスポンスは届けられる。ルートが増えるほど型の計算が重くなる(ルートごとに、アプリ全体の型を作り直すため)
- **本体のサイズ:** 戻り値を `this` にするだけなので、ほぼ増えない(数十バイト)
- **Ippo:** ルートが「アプリの型の一部」としてしか存在しないので、loader やサーバー関数 1 つ分の型を取り出すのに、型の掘り出しが要る

#### 案 B: ルートをまとめて定義する形(今の `app.routes()` を伸ばす)

Senri には、表の形でまとめて登録する `app.routes({ "GET /hello": handler })` が既にある。この表を、型を持ったまま外に出せるようにする。

```ts
import { createApp, defineRoutes } from "@senrijs/senri";

export const routes = defineRoutes({
    "GET /users/:id": ({ id }) => ({ id, name: "a" }),
    "POST /users": { body: userSchema, handler: (_, c) => ({ created: c.valid("body") }) },
});
export type Api = typeof routes;

const app = createApp();
app.routes(routes);

// クライアント(@senrijs/senri/client)
const api = client<Api>("https://example.com");
const user = await api("GET /users/:id", { params: { id: "1" } });
```

- **今の書き方:** 壊さない。`app.get()` はそのまま使える(ただし、そのルートはクライアントの型に入らない)。型が欲しいルートだけ表に移せばよい
- **今の表との違い:** 今の `app.routes()` の表は、値がハンドラーだけで、スキーマを付けられない(`RouteTable` の型も、ハンドラーの戻り値の型を捨てている)。案 B では、値に `{ params, query, body, handler }` の形を足し、戻り値の型を保つ
- **まとめ方:** 表は普通のオブジェクトなので、ファイルごとに分けて合わせられる(`{ ...userRoutes, ...postRoutes }`)。プレフィックスは `prefix("/api", routes)` のような関数で、キーごと付け直す(型もテンプレートリテラル型で付け直す)
- **型:** キー(`"GET /users/:id"`)からメソッドとパスとパラメーターが決まる。表は 1 つのオブジェクトリテラルなので、型は一度で決まり、ルートが増えても作り直しがない。ハンドラーの戻り値の型を保つよう、`RouteTable` の型を作り直す(型だけの変更)
- **クライアントの呼び方:** サーバーの表と同じ `"GET /users/:id"` という文字列で呼ぶ。Proxy を使わないので、クライアントの実行時のコードが小さい(パスにパラメーターを入れ、クエリとボディを付けて `fetch` するだけ)。文字列なので、検索でサーバーのルートとすぐ結び付く
- **本体のサイズ:** `defineRoutes` は、受け取った表をそのまま返す関数(型を付けるためだけ)。本体はほぼ増えない。クライアントは別の入口
- **Ippo:** 表の 1 つ 1 つが独立した定義なので、`typeof routes["GET /users/:id"]` で 1 つのルートの入力と出力の型を取り出せる。loader(GET)やサーバー関数(POST)の型にそのまま使える
- **OpenAPI(2 で詳しく):** 表は実行時にも一覧できて、スキーマも横にあるので、そのまま元にできる

#### 案 C: 型を生成する形

今の書き方はそのままにして、ビルドの前にアプリを読み、ルートの型をファイルに書き出す。

```sh
senri gen client ./src/app.ts > ./client/api.d.ts
```

- **今の書き方:** まったく変えなくてよい
- **型:** メソッド・パス・パラメーター・スキーマは、実行時にアプリから取れる(`app.routeList()` とスキーマ)。しかし**レスポンスの型(ハンドラーの戻り値)は実行時には分からない**ので、TypeScript のコンパイラー API で読む必要がある。重く、壊れやすい
- **開発の流れ:** サーバーを変えるたびに生成し直す。忘れると、型が古いまま通ってしまう(CI で確かめる仕組みが要る)
- **本体のサイズ:** 増えない(生成の道具は別のパッケージ)
- **Ippo:** 生成したファイルを読めば使えるが、メタフレームワークの中で生成の手順を持つことになる

### 1.4 比べ

| | 案 A: つなげて書く | 案 B: まとめて定義 | 案 C: 型を生成 |
|---|---|---|---|
| 今の書き方を壊さないか | 壊さない(型が欲しければ全部書き直し) | 壊さない(欲しいルートだけ表へ) | 壊さない |
| 書き忘れたとき | 黙って型から消える | 表にないルートは、クライアントに出ない(はっきりしている) | 生成し忘れると古い型のまま |
| パラメーター・クエリ・ボディ | 届く | 届く | 届く |
| レスポンスの型 | 届く | 届く | コンパイラー API が要る |
| 型の重さ(ルートが多いとき) | 重い(Hono が公式に注意) | 軽い(一度で決まる) | 軽い(生成済み) |
| 本体のサイズ | ほぼ増えない | ほぼ増えない | 増えない |
| クライアントの実行時のコード | Proxy | 関数 1 つ | 関数 1 つ(生成物) |
| OpenAPI の元にできるか | アプリの中を一覧すれば | 表をそのまま使える | 生成の道具の中で |
| Ippo の loader・サーバー関数 | 型の掘り出しが要る | 1 つずつ取り出せる | 生成物から |

### 1.5 おすすめ: 案 B(ルートをまとめて定義する形)

理由:

1. **今の Senri の上に自然に乗る。** 表の形の `app.routes()` は既にある。新しい書き方を足すのではなく、今あるものに型を持たせる
2. **壊す変更がない。** `app.get()` の書き方はそのまま残る。型付きクライアントが欲しいルートだけ、表に移せばよい
3. **型が軽い。** Hono が公式に注意している「ルートが増えると tsserver が重い」問題を、作りの段階で避けられる
4. **書き忘れに気づける。** 「つなげ忘れて型が黙って消える」ことがない。表にあるものが、クライアントに出るもの
5. **2〜3 と Ippo にそのまま使える。** 表は実行時にも一覧できて、スキーマも横にあるので、OpenAPI とテスト用ヘルパーの元になる。1 つのルートの型を取り出せるので、Ippo の loader やサーバー関数にも使える

決めること・確かめること(OK をもらったら詰める):

- 表の値の書き方: ハンドラーだけ(`"GET /x": handler`)と、スキーマ付き(`"POST /x": { body, handler }`)。今の `app.get(path, schemas, handler)` の 3 つの引数の形と、どうそろえるか
- レスポンスの status ごとの型: `c.json(x, 404)` のように status を型に残す道を作るか、成功の型だけにするか
- `onError`・`notFound`・ミドルウェアの応答の型: Hono と同じく、自動では入れない(入れる道だけ用意する)か
- JSON にしたときの型(`Date` は文字列になる、など)を、クライアントの型でどこまで直すか
- 型の重さを確かめる: 200 ルートの表で、tsserver の時間を測る
- クライアントの大きさの目標(minify 後、gzip 後)

### 1.6 本体のサイズについて(確かめたいこと)

「本体は minify 後 12KB 以下が必達」と言われているが、今(0.2.21)の本体は、`bun run size` の「hi」アプリで **minify 後 16.1 KB(gzip 6.3 KB)**。README にも「minify して約 16KB」とある。12KB が何の数字か(gzip 前か後か、どのアプリで測るか)を決めてから、案 B で増える分を測る。案 B では、本体に足すのは `defineRoutes`(表をそのまま返す関数)と、表を受けるときのわずかな処理だけになる見込み。
