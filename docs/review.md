# Senri レビュー

コードは変更していません。✅ の付いた項目は、スクラッチ領域のスクリプトで Bun / Node / Deno 上で実際に再現を確認したものです。

## 🔴 致命的（すぐ直すべき）

**1. [マルチランタイム・セキュリティ] 不正な Host ヘッダーのリクエスト1本で、Node のプロセスが落ちる ✅**
[adapters/node/index.ts:9-26](adapters/node/index.ts#L9-L26)
- `Host: a b` を送ると `new Request` が TypeError を投げます。async リスナーに try/catch がないため、unhandled rejection で exit 1 になりました。
- 外部から1リクエストで止められる DoS です。
- 同じ箇所に関連する問題があります:
  - Host がないと `http://undefined/...` になる
  - absolute-form の `req.url` では URL が壊れる
  - プロトコルが常に `http` になる
- `app.fetch` や `arrayBuffer()` が失敗した場合も、同じように落ちます。

**2. [マルチランタイム] Node でリクエストボディが届かない ✅**
- `POST "hello"` を送っても、`c.req.text()` は `""` でした。
- `new Request` に `body` を渡していないのが原因です。
- 修正案: GET/HEAD 以外では `body: Readable.toWeb(req)` と `duplex: "half"` を渡す。

**3. [ルーティング] 静的パス優先が、登録順によって崩れる ✅（3ランタイムとも）**
[index.ts:102-117](src/index.ts#L102-L117)
- `compareRoutes` は短いほうの長さまでしか比べず、長さの違うルート同士だと `0` を返します。順序の一貫性が崩れるので、sort が当てになりません。
- 例: `/users/:id` → `/users` → `/users/me` の順で登録すると、`/users/me` へのリクエストが `param me` になります。
- [examples/shared/app.ts](examples/shared/app.ts) も長さの違うルートが混ざっています。今のテストはルートが2本だけなので通っています。
- 修正案: セグメント数を第1キーにする（マッチ時は長さの一致が前提なので）。または trie にする。

**4. [セキュリティ] `//admin` で認証を素通りできる ✅**
- ルーターは `filter(Boolean)` で空セグメントを潰しますが、ミドルウェアは生の `pathname` を見ています。
- そのため `startsWith("/admin")` をすり抜けたうえで、`/admin` ルートにはマッチします。
- 今後パーセントデコードを入れると、`/%61dmin` でも同じことが起きます。
- 修正案:
  - 正規化したパスを `c.path` として1か所で持ち、ルーターとミドルウェアの両方がそれを使う
  - ルート単位・パス単位のミドルウェアを用意する

## 🟠 高

**5. [セキュリティ] 500 のレスポンスで `err.message` をそのまま返している ✅**
- [index.ts:184](src/index.ts#L184): 試しに投げた `db password=hunter2` が、クライアントにそのまま見えました。
- 詳細は開発モードのときだけ出すべきです。

**6. [セキュリティ] 404 の「もしかして」が、本番でルート名を漏らし、CPU も使い潰せる ✅**
- ルート50本・8KB のパスで、404 が1回あたり約190ms かかりました。そのたびに大きな配列を確保しています。
- 修正案: 開発モード限定にする、パス長の上限を設ける、距離が閾値を超えたら打ち切る。

**7. [ルーティング] パーセントエンコードを扱っていない ✅**
- `/こんにちは` が 404 になります。
- `/u/山田` の `id` が `%E5%B1%B1%E7%94%B0` になります。
- 修正案: セグメントに分割してから `decodeURIComponent` する。`%E0%A4%A` のような不正な値で出る URIError は 400 にする。

**8. [Context] ヘッダーが消える・混ざる ✅**
- `c.header()` が無視される場面があります:
  - ハンドラが `Response` を直接返したとき
  - 404 / 405 / 500 のとき（CORS ヘッダーがエラー時に付かない）
- `c.json()` は共有の `#headers` に Content-Type を書き込みます。その後に `c.text()` を呼ぶと `application/json` のままでした。
- `next()` の後にミドルウェアで `c.header()` しても反映されません。ダッシュボードで `Server-Timing` を付けようとすると、ここで困ります。
- 修正案: Context に `c.res` を持たせ、dispatch の最後に一度だけヘッダーをマージする。

**9. [マルチランタイム] Node で Set-Cookie が最後の1つしか残らない ✅**
- `forEach` の中で `setHeader` を呼んでいるため、上書きされます。
- 修正案: `getSetCookie()` で取り出し、配列で `setHeader` する。

**10. [ミドルウェア] `next()` の扱いが緩い ✅**
- 2回呼ぶと、ハンドラが2回実行されました。
- `await` せずに `next()` だけ呼ぶと、500 を返したうえでハンドラが裏で走り続けます。しかもこの書き方は型チェックを通ります。
- 修正案: dispatch で呼び出し位置を追い、Koa / Hono と同じく二重呼び出しで throw する。

**11. [エラー処理] try の外で例外が起きる ✅**
- [index.ts:246](src/index.ts#L246) の `c.toResponse(result)` が try の外にあります。ミドルウェアが BigInt を含む値を返すと、`app.fetch` 自体が reject しました。
- Node では、これが項目1と同じクラッシュにつながります。
- `hadle` 内の `new URL` も同様に try の外です。

**12. [ルーティング] HEAD リクエストが 405 になる ✅**
- `curl -I` や死活監視が失敗します。
- 修正案: HEAD は GET にフォールバックし、ボディを捨てる。OPTIONS の既定の挙動も決めておく。

## 🟡 中

**13. [型] `HandlerResult` の `object` が広すぎる ✅**
- `Blob` を返すと `{}` になりました。
- 関数を返す（呼び忘れ）と、空ボディ + `application/json` になりました。
- どちらも型チェックを通ります。ReadableStream / ArrayBuffer も同じ扱いになるはずです。

**14. [型] `routes()` のテーブル形式ではパラメーターが推論されない ✅**
- `{ "GET /u/:id": ({ id, nope }) => … }` が型を通ります。
- 修正案: mapped type でキーからパスを取り出し、パラメーターを推論する。

**15. [型] 型と実行時の挙動がずれる ✅**
- `/time/12:00` は、型では `{ "00": string }` になりますが、実行時は静的セグメントとして扱われます。
  - 修正案: `/` で分割してから、セグメントの先頭が `:` かどうかで判定する。
- 非リテラルの `string` をパスに渡すと、params が `{}` になって何も触れません。
  - 修正案: `Record<string, string>` にフォールバックする。
- `/a/:id/b/:id` のような重複したパラメーター名が、黙って上書きされます。

**16. [ルーティング] 重複登録と細かい仕様**
- 同じルートを重複登録しても黙って先勝ちになり、Allow ヘッダーが `GET, GET` になりました ✅
- 末尾スラッシュや `//` を同じパスとして扱う挙動は、仕様として明文化したほうがよいです（項目4と関係します）。
- `put` / `patch` / `all` がありません。logger には PUT と PATCH の色だけ用意されています。

**17. [マルチランタイム] Node アダプターがレスポンスを全部バッファしている**
- `arrayBuffer()` で丸ごと読んでいるので、SSE やダッシュボードのライブ更新ができません。
- クライアント切断時の AbortSignal もありません。

## 🔵 設計：今のうちに直しておきたいこと

**18. レスポンスを作る場所が分散している**
- 404 / 405 / 500 のレスポンスが4か所でハードコードされています（[181](src/index.ts#L181), [207](src/index.ts#L207), [228](src/index.ts#L228), [248](src/index.ts#L248)）。エラーページを足すと、ここがネックになります。
- 修正案:
  - `app.onError` / `app.notFound` フックと、ステータス付きの `HttpError` を用意する
  - エラーページは、そのフックの開発モード向け実装にする（コアに HTML を入れない）
- ファイル構成の案: `context.ts` / `router.ts` / `compose.ts` / `errors.ts` / `app.ts` / `dev/`
- `logger.ts` と `index.ts` が循環 import になっています。今は型だけなので無害ですが、`context.ts` を分ければ解消します。

**19. ダッシュボードの前提がまだない**
- dispatch が `fetch` 内のクロージャになっていて、計測を差し込む場所がありません。
- 「通過時間」を出すなら、`next()` の中の時間を引いた self time にすべきです。そうしないと、外側の logger が常に一番遅く見えます。また `Date.now()` ではなく `performance.now()` を使うべきです。
- ミドルウェアに名前がありません。`logger()` は無名のアロー関数を返すので、名前が `""` になります。
- マッチしたルートパターンと params が Context にありません。ログやダッシュボードを `/users/:id` 単位で集計できません。
- ミドルウェア間で値を渡す型付きの仕組み（`c.set` / `c.get` など）がありません。

**20. 開発モードと `/_senri` の安全性**
- 開発モードをコアで環境変数から判定しないほうがよいです。Deno は `--allow-env` がないと読み取りでエラーになり、今の `deno.json` は `--allow-net` だけです。
- `createApp({ dev: true })` のような明示オプションにし、既定は本番扱いにするのがおすすめです。
- `/_senri` は開発時だけ有効にし、できればループバックからのアクセスに限定します。
- エラーページに path や message を埋め込むときは、必ずエスケープしてください。404 は今もリクエストのパスをそのまま返しているので、HTML にした瞬間に反射型 XSS になります。

**21. 配布形態**
- `exports` が `.ts` を直接指しています。Node は node_modules 内の `.ts` の型除去を拒否するので、npm で公開すると Node から使えません。
- `adapters/node` も `exports` に入っていません。
- 公開前に、ビルド（`.js` + `.d.ts`）か JSR を検討してください。

**22. CI とテスト**
- `bun check` は root の tsconfig しか見ていません。対象は src の2ファイルだけで、test / adapters / examples は CI で型チェックされていません ✅（今は全部通ります）。
- Node アダプターのテストがありません。項目1・2・9 はテストがあれば見つかっていたはずです。
- smoke テストは `GET /hello` の1本だけです。

## ⚪ 低
- `c.text()` が Content-Type を明示していません。Bun では `app.fetch` の結果のヘッダーが `null`、Node / Deno では `text/plain;charset=UTF-8` になり、ランタイムによってテスト結果が変わります。実際に送られるヘッダーはどちらも同じです。
- logger の色が既定でオンなので、非 TTY 環境では ANSI のエスケープコードがログに混ざります。TTY 判定はランタイムごとに違うので、オプションで渡す形がよいです。
- `hadle` のタイポ、README が古い（`bun run index.ts` は存在しない）。

**優先順位:** まず 1〜4 です。そのうえで、エラーページやダッシュボードに着手する前に 8・18・19（レスポンスの最終化・フック・計測ポイント・`c.route`）の土台を作っておくと、あとの機能追加がずっと楽になります。
